# Plan: Ask Worthfolio — grounded answers about your forecast

## Product decision

Build this as a focused insight feature, not a general-purpose financial
chatbot.

Users should be able to ask a small, well-defined set of questions in plain
language and receive an answer grounded in their recorded data or in the exact
output of Worthfolio's forecast engine. Worthfolio pays for the AI usage. Users
never create, enter, or manage an API key.

The first release is deliberately narrow:

- read-only with respect to financial data and scenarios;
- approximately ten supported question types;
- deterministic calculations executed locally in the browser;
- a secure server-side OpenAI gateway;
- evidence and assumptions displayed with every substantive answer;
- device-local conversation history only;
- no voice input, financial advice, or model-driven UI actions.

The value proposition is not “chat with your finances.” It is: **get a clear,
trustworthy explanation of what your numbers and assumptions imply.**

---

## Product principles

### Worthfolio computes; the model interprets

The language model identifies what the user is asking and helps phrase the
answer. It does not compound balances, calculate deltas, find crossings, or
invent values.

Every numeric result comes from a local deterministic function and carries an
evidence id. The final UI renders canonical numbers from those evidence records
rather than trusting numeric text generated by the model.

### “Exact” has a limited meaning

An answer can be exact relative to the current forecast engine and still rest
on weak or incomplete financial assumptions. Every result must distinguish:

- `recorded` — a value explicitly present in a saved snapshot;
- `derived` — a deterministic calculation over recorded values;
- `forecast` — output from the forecast engine;
- `unknown` — the required underlying data is absent or incomplete.

Forecast answers must identify their origin month and the assumptions that
materially affect them. Missing data is never silently represented as zero in
the chat layer.

### Minimize disclosure and cost

Do not send the complete 75-year forecast with every question. Send a compact
manifest that lets the model resolve names and choose a tool, then disclose
only the values required to answer that question.

### Trust is part of the interface

Users should be able to see where an answer came from without inspecting a
debug transcript. Recorded dates, forecast dates, scenario names, assumptions,
and data-quality warnings are first-class UI.

## Supported questions for v1

Implementation starts with a capability matrix. Each supported intent must
define its required data, local calculation, evidence shape, wording rules,
and insufficient-data behavior.

| Intent | Example | Local result | Required caveat |
|---|---|---|---|
| Net worth at date | “What might I be worth in 2036?” | Net worth for an exact month | Forecast assumptions for future dates |
| Goal timing | “When might I reach $1M?” | First forecast crossing | “If current assumptions continue” |
| Goal status | “Am I on track for my goal?” | Current/forecast value versus saved goal | Define what “on track” means |
| Account balance at date | “What might my Roth be worth in 2040?” | Exact account value for a month | Growth and contribution assumptions |
| Liability trajectory | “When does the Visa reach zero?” | First modeled zero crossing | Not a loan amortization or payment schedule |
| Historical balance change | “How much did brokerage change last year?” | Endpoint balance delta | Call it balance change, not investment return |
| Largest historical mover | “What changed my net worth most?” | Ranked recorded balance deltas | Flag incomplete snapshots |
| Category contribution | “Which category is dragging me down?” | Defined category delta/ranking | State the comparison window |
| Scenario comparison | “How do Default and Market Downturn compare in 10 years?” | Same-month scenario values and delta | Identify assumptions that differ |
| Assumption summary | “What is this forecast assuming?” | Growth and contribution assumptions | No prediction language |

Before implementation, settle exact definitions for “on track,” “dragging me
down,” contribution windows, and data completeness. Ambiguous questions should
trigger one concise clarification or use a clearly stated default window.

### Unsupported in v1

- Investment, tax, legal, or debt-management advice
- Claims about actual investment return when only balances are known
- Cash-flow planning or dated future events the engine cannot represent
- Creating or editing accounts, balances, contributions, goals, or scenarios
- Navigation or other model-driven UI actions
- Questions requiring external financial or market data
- Open-ended questions outside the capability matrix

Unsupported requests get a direct explanation plus a nearby supported question
when one exists.

## Architecture

### Request path

```text
Browser
  ├─ keeps the decrypted vault in memory
  ├─ builds a compact account/scenario manifest
  ├─ executes forecast and lookup tools locally
  └─ validates evidence and renders canonical values
        │
        ▼
Supabase Edge Function
  ├─ verifies the user's Supabase JWT
  ├─ enforces quotas, size limits, and tool-loop limits
  ├─ holds the OpenAI API key in server-side secrets
  ├─ pins the approved model and request settings
  └─ forwards only the permitted request shape
        │
        ▼
OpenAI Responses API
```

The Edge Function is a stateless gateway, not a financial-data store. It will
necessarily process the plaintext fields being sent to OpenAI, so the consent
copy must say that plainly. Request bodies, tool outputs, and model responses
must not be written to application logs.

### Gateway controls

The browser never receives the OpenAI key and cannot choose arbitrary models,
tools, prompts, token limits, or provider parameters.

The Edge Function must enforce:

- authenticated users only;
- an allowlisted request schema;
- a pinned model configured server-side;
- per-user burst and monthly quotas;
- maximum input and output sizes;
- a small maximum number of tool rounds per question;
- timeouts and cancellation;
- origin/CORS restrictions;
- `store: false` for model requests;
- sanitized errors that do not expose secrets;
- usage metrics without financial payload contents;
- a global feature flag and spend kill switch.

Do not depend on prompt caching for the unit economics. If used, cache only the
static system instructions and tool schemas with an explicit breakpoint before
any user-specific financial data. Measure actual cached tokens in production.

### Tool-calling loop

1. The browser sends the user's question and compact manifest to the gateway.
2. The model returns either a supported intent or a strict-schema tool call.
3. The browser validates the tool name and every argument against local ids,
   date bounds, and allowed enum values.
4. The browser executes the deterministic tool against the active scenario.
5. The browser sends the bounded tool result and call id through the gateway.
6. The model returns a structured answer referencing evidence ids.
7. The browser validates the structure and renders canonical facts locally.

Stop after the configured tool-round limit. Never retry malformed arguments by
guessing. Show a recoverable error when the gateway, provider, or local tool
cannot complete the request.

## Local forecast and evidence layer

### Phase-zero extraction

Move these pure functions out of `src/pages/Dashboard.jsx` into
`src/lib/forecast.js` without changing chart behavior:

- `MAX_FORECAST_MONTHS`
- `monthIndex`
- `customForecastCount`
- `buildAccountModels`
- `generateForecast`

Both Dashboard and Ask Worthfolio must call the same implementation. The
existing 900-month ceiling remains available to tools, but it is not serialized
into every AI request.

### Data-quality work before chat

The chat layer must not inherit “missing means zero” semantics unnoticed. Add
helpers that report:

- first and last recorded month;
- whether a requested snapshot contains every active account;
- which accounts are missing for a month or comparison window;
- whether contribution history is present and over what window;
- whether a forecast origin is stale relative to the calendar month;
- invalid or unsupported growth-rate values;
- whether a result is recorded, derived, forecast, or unknown.

A user with categories but no recorded balances receives “I need at least one
recorded balance month” rather than a projection starting from zero.

### Forecast semantics that must be disclosed

The current engine applies a fixed annual growth rate, converts it to a monthly
rate, uses an average recorded contribution, rounds monthly, and honors explicit
future overrides. That is the source of truth for v1, but answers must not imply
more sophisticated behavior.

In particular, a liability's negative growth rate is not an APR/payment
amortization model. Phrase its crossing as “the month this Worthfolio scenario
models the balance reaching zero,” never as a guaranteed payoff date.

### Local tools

Use a small, strict set of read-only tools:

| Tool | Purpose |
|---|---|
| `get_value(target, month)` | One account, category, or net-worth value at an exact month |
| `get_series(target, from, to, step)` | A bounded recorded or forecast series |
| `find_crossing(target, threshold, direction)` | First supported threshold crossing |
| `compare_scenarios(month, scenarioIds)` | Same-month scenario comparison |
| `get_assumptions(targetIds)` | Growth, contribution, origin, and quality metadata |

Tool arguments use ids, not free-form account names. Tool implementations reject
unknown ids, malformed months, inverted windows, excessive ranges, and dates
outside the supported recorded/forecast horizon.

Every returned fact has a stable evidence record:

```js
{
  id: 'forecast:default:netWorth:2036-08',
  kind: 'forecast',
  metric: 'netWorth',
  targetId: 'portfolio',
  scenarioId: 'default',
  month: '2036-08',
  value: 812400,
  display: '$812,400',
  assumptions: ['origin:2026-08', 'growth-and-contributions-continue'],
  quality: { complete: true, warnings: [] },
}
```

### Structured answer contract

The model returns a strict schema, not unrestricted Markdown. It may write
short explanatory text, but numeric values shown to the user are evidence
references rendered by the client.

```js
{
  status: 'answered' | 'needs_clarification' | 'unsupported' | 'insufficient_data',
  intro: 'At your current assumptions, your projected net worth is',
  facts: [{ evidenceId: 'forecast:default:netWorth:2036-08' }],
  explanation: 'This uses the growth and contribution assumptions in Default.',
  caveatCodes: ['LONG_RANGE_FORECAST'],
  evidenceIds: ['forecast:default:netWorth:2036-08'],
}
```

Validation fails closed if the model references unknown evidence, emits numeric
claims outside canonical fact fields, or omits a required caveat. This replaces
the proposed regex-based “number check,” which cannot detect a real value
attributed to the wrong month or account.

Starter questions with known parameters may skip the model's intent step and
invoke the same local tools directly.

## Compact manifest

The per-question manifest contains enough information to resolve the user's
language without carrying the forecast itself:

```js
{
  calendarMonth: '2026-08',
  activeScenario: { id: 'default', name: 'Default Scenario', linked: true },
  scenarios: [{ id, name }],
  categories: [
    {
      id,
      name,
      type: 'asset' | 'liability',
      accounts: [{ id, name }],
    },
  ],
  coverage: {
    firstRecordedMonth: '2025-09',
    lastRecordedMonth: '2026-08',
    incompleteMonths: 2,
    forecastEnd: '2101-08',
  },
  goal: { configured: true },
  supportedIntents: [/* stable ids */],
}
```

Real names are included so “How is my Roth doing?” can resolve to the right
account. Balances, history, contributions, and full forecasts are omitted until
a specific tool result requires them.

Account, category, and scenario names are untrusted user data. Keep them in
structured fields, clearly separated from instructions, and render model output
as plain text or sanitized components—never unsanitized HTML.

## Privacy and consent

Ask Worthfolio is off until the user explicitly enables it. The consent screen
must state:

- Worthfolio sends the question and relevant decrypted financial data through
  its secure gateway to OpenAI;
- the gateway can process the plaintext necessary to make the request;
- which classes of data may be sent, including real account and scenario names;
- OpenAI's applicable retention and abuse-monitoring behavior;
- API data is not used to train OpenAI models unless the API account opts in;
- disabling the feature stops future requests but cannot retract already
  processed requests;
- answers are explanations of Worthfolio data, not financial advice.

The setting remains revisitable. Disabling it clears the device-local chat
history and hides the entry point after confirmation.

Do not use OpenAI-hosted conversations for v1. Send `store: false` and replay
only the bounded device-local transcript needed for conversational continuity.

The landing page and privacy policy should explain that end-to-end encryption
protects vault sync, while user-initiated AI questions disclose selected
decrypted data to the named AI provider.

---

## Conversation storage

For v1, transcripts are device-local and scoped by user id plus scenario id.
Cap them by both turn count and total characters, trimming complete oldest
turn-pairs rather than individual messages.

Streaming partials stay in React state. Persist the assistant message only when
the turn completes successfully. Do not store briefing manifests, raw tool
payloads, hidden instructions, or provider response objects in the transcript.

Cross-device transcript sync is postponed. The current vault is a single
encrypted, last-write-wins blob; adding frequently changing chat data would
increase the risk of one device overwriting another device's financial edits.
Sync can be reconsidered after the vault has conflict detection/merging or an
encrypted append-only message design.

## UX

- “Ask Worthfolio” opens as a full-height sheet on mobile and a right-hand
  drawer on desktop.
- The active scenario name is always visible in the header.
- The empty state leads with supported starter questions, not an empty chatbot.
- During tool use, show a specific status such as “Checking your 2036 forecast.”
- Answers show evidence rows with month, scenario, and `Recorded`, `Derived`, or
  `Forecast` labels.
- Forecast answers expose their key assumptions and stale-data warnings.
- Unsupported or insufficient-data states are designed responses, not generic
  errors.
- Switching scenarios swaps to that device's scenario-specific thread.
- Provide “Clear conversation” and “Disable Ask Worthfolio” controls.

Voice input, navigation actions, arbitrary Markdown, and cross-device chat are
out of scope for v1.

## Cost and abuse controls

Because Worthfolio pays for usage, cost control is a product requirement:

- use an evaluated fast/efficient model rather than a user-selectable model;
- pin the approved model snapshot or controlled server-side alias;
- bound transcript, manifest, tool output, and response sizes;
- cap tool rounds and retries;
- enforce per-user daily/monthly quotas;
- add global daily spend alerts and a kill switch;
- measure input, cached input, output, tool rounds, latency, and errors;
- never include financial content in analytics events;
- consider a small free allowance and higher paid-plan quota after the pilot.

The model choice is an operational setting owned by the server, not a control in
the consumer UI. Change it only after running the grounded-answer evaluation
suite against the candidate model.

## Testing and evaluation

Add Vitest before extracting the forecast engine. Cover:

- forecast parity with the existing Dashboard;
- all supported derived metrics and crossings;
- missing and partial snapshot behavior;
- stale origins and empty history;
- contribution-history edge cases;
- invalid growth values and date bounds;
- evidence-id generation and canonical formatting;
- structured-answer validation and fail-closed behavior;
- tool argument validation;
- transcript trimming by complete turn pairs.

Add gateway tests with the OpenAI call mocked:

- authentication and CORS;
- quotas and size limits;
- model/parameter allowlisting;
- tool-round limit;
- `store: false` enforcement;
- timeout, cancellation, provider errors, and safe error messages;
- confirmation that request bodies are absent from logs.

Create a versioned evaluation set covering every supported intent, ambiguity,
missing-data state, duplicate account name, malformed tool call, wrong evidence
reference, and prompt-injection attempt through user-controlled names.

The release gate is not “the model usually answers correctly.” It is:

- every displayed number came from validated local evidence;
- every supported answer uses the correct scenario, target, and month;
- required caveats appear;
- unsupported and insufficient-data questions fail safely;
- cost and latency stay within the pilot budget.

## Delivery phases

| Phase | Scope |
|---|---|
| **0 — Truth contract** | Finalize supported intents, definitions, caveats, evidence schema, and eval cases |
| **1 — Forecast library** | Add Vitest; extract `forecast.js`; prove Dashboard parity; add data-quality helpers |
| **2 — Local answer engine** | Implement strict tools, evidence records, deterministic starter-question answers, and structured rendering |
| **3 — Secure gateway** | Deploy the authenticated Edge Function with server-held key, quotas, limits, privacy settings, and observability |
| **4 — Language layer** | Add intent/tool orchestration, strict structured output, validation, and the full eval suite |
| **5 — Product UX** | Drawer/sheet, starter questions, evidence UI, assumptions, consent, device-local threads, and error states |
| **6 — Pilot** | Feature-flagged rollout; measure usefulness, grounding failures, latency, and cost before widening access |

Phases 0–2 deliver useful deterministic insight cards even if the AI layer is
delayed. Do not begin broad UI polish until the evidence contract and secure
gateway pass their release gates.

---

## Success criteria

The feature earns broader rollout when pilot users can answer the supported
questions faster than by inspecting charts manually, understand why the answer
is trustworthy, and return to use it more than once.

Track:

- percentage of questions matched to a supported intent;
- successful grounded-answer rate;
- clarification, unsupported, and insufficient-data rates;
- evidence/validation failures;
- repeat usage and starter-question selection;
- latency by direct versus tool-assisted answer;
- cost per completed answer and per active user;
- disable/clear rates and privacy-related support feedback.

Do not optimize for conversation length. A short interaction that gives the
user a trustworthy answer is the desired outcome.

## Decisions settled

| Question | Decision |
|---|---|
| User value | Focused answers and explanations, not an open-ended chatbot |
| API cost | Paid by Worthfolio; users never handle a key |
| API-key location | Server-side secret in a Supabase Edge Function |
| Financial calculations | Deterministic and local in the browser |
| Model role | Intent interpretation and concise narration |
| Numeric grounding | Evidence ids plus client-rendered canonical values |
| Request payload | Compact manifest plus on-demand tool results |
| Horizon | Engine supports 900 months; never sent eagerly in full |
| Account names | Real names in the manifest, disclosed during consent |
| Provider storage | Responses requests use `store: false` |
| Transcripts | Device-local and bounded for v1 |
| Cross-device chat | Deferred until encrypted sync has conflict handling |
| Model choice | Pinned and controlled server-side, changed only through evals |
| Voice and actions | Out of scope for v1 |
